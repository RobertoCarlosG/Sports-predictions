## TABLAS EN BD (Supabase PostgreSQL)

prediction_results      Caché de predicciones ya calculadas
admin_users             Usuarios del panel admin
model_versions          Registro de versiones del modelo


## COLUMNAS DE game_feature_snapshots (las 13 features del modelo)

home_wins_roll          Tasa de victorias local (ventana rolling)
away_wins_roll          Tasa de victorias visitante (ventana rolling)
home_runs_avg_roll      Promedio de carreras local (rolling)
away_runs_avg_roll      Promedio de carreras visitante (rolling)
temperature_c           Temperatura del estadio
humidity_pct            Humedad
wind_speed_mps          Viento
elevation_m             Altitud del estadio
home_starter_era        ERA del abridor local
away_starter_era        ERA del abridor visitante
home_bullpen_era        ERA del bullpen local
away_bullpen_era        ERA del bullpen visitante
defaults_injected       Flag 0/1: ¿se usaron constantes por falta de datos reales?

Columnas de etiqueta (solo para training):
home_win                1 = ganó local, 0 = ganó visitante
total_runs              Total de carreras del partido


## MODELO ML

Tipo activo:       Random Forest Classifier (clf) + Random Forest Regressor (reg)
Versión:           rf-db-v1
Archivo:           backend/src/app/ml/artifacts/model.joblib
n_estimators:      128 árboles
n_features_in_:    13
Entrenado con:     game_feature_snapshots + games (datos reales de BD)

Modelo XGBoost alternativo: model_xgb.joblib (xgb-db-v1), con calibración isotónica.

IMPORTANTE: también existe training.py::train_default_model() que genera un modelo
SINTÉTICO ("rf-synthetic-v0") entrenado con datos Gaussianos aleatorios. Este modelo
se usa solo como placeholder cuando no hay model.joblib. No predice partidos reales.


## PIPELINE DE DATOS (orden obligatorio)

1. IMPORTAR PARTIDOS (backfill)
   Admin → "Importar fechas" / endpoint POST /admin/pipeline/import-games
   Descarga resultados históricos de MLB API → tabla `games` + `game_weather`

2. RECALCULAR INDICADORES (rebuild_feature_snapshots)
   Admin → "Recalcular indicadores" / POST /admin/pipeline/rebuild-snapshots
   Calcula rolling stats + ERA para cada partido → tabla `game_feature_snapshots`
   Sin este paso los snapshots están vacíos y las predicciones usan constantes → ~50%

3. ENTRENAR MODELO (train_from_db)
   CLI: cd backend && uv run python -m app.ml.train_from_db
   O desde panel admin → "Entrenar modelo"
   Lee game_feature_snapshots con home_win y total_runs NO NULL → entrena RF/XGB
   Requiere mínimo 20 partidos etiquetados

4. RECARGAR MODELO
   Admin → "Recargar modelo" / POST /admin/model/reload
   Carga el nuevo model.joblib en memoria sin reiniciar el servidor

5. ETL DIARIO (automático o manual)
   POST /admin/pipeline/mlb-daily-snapshot
   Ejecuta sync hoy+mañana + rebuild snapshots + limpia caché de predicciones


## POR QUÉ SIEMPRE VES ~50%

Causa raíz: los partidos de hoy NO tienen fila en game_feature_snapshots
(o la tienen pero con home_wins_roll, away_wins_roll, etc. = NULL).

Cuando snapshot es None o tiene campos nulos, features.py inyecta constantes SIMÉTRICAS:
  home_wins_roll = 0.5   away_wins_roll = 0.5   (idénticos)
  home_runs_avg  = 4.5   away_runs_avg  = 4.5   (idénticos)
  home_starter_era = 4.5 away_starter_era = 4.5 (idénticos)
  home_bullpen_era = 4.2 away_bullpen_era = 4.2 (idénticos)

Con features idénticas para local y visitante, el modelo no tiene información para
diferenciarlos → devuelve probabilidad cercana a 50% para todos los partidos.

El modelo (rf-db-v1) ES real y fue entrenado con datos históricos. El problema no es
el modelo sino que en inferencia no tiene datos de entrada reales.

## PROBLEMAS CONOCIDOS / INCIDENTES

1. BOM UTF-8 (jun 2026)
   Commit 3ac7597 introdujo BOM (EF BB BF) en pyproject.toml y 8 archivos más.
   tomllib lo rechaza → el build de Render falla con "Invalid statement at line 1, col 1".
   Fix: eliminar BOM; quien lo introduce usa un editor con "UTF-8 con BOM" (VS Code: "files.encoding": "utf8").

2. Supabase free-tier egress
   En MVP1 se superó el límite de GB del plan free de Supabase.
   Render fue diferido como medida de ahorro.

3. sklearn version mismatch
   model.joblib se generó con sklearn 1.9.0; el entorno local tiene 1.8.0.
   Causa InconsistentVersionWarning pero no rompe la inferencia.
   Regenerar el modelo en el mismo entorno resuelve la advertencia.
